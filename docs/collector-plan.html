Signals open-source collector and dashboard

A single Rust binary that receives events from the Signals SDKs, stores them in Postgres, rolls them up and serves a dashboard: who connected, which tools were called, how fast, how often they failed. Self-hostable with one docker compose up; the same binary runs mcpramen's hosted service. Companion documents: Plan 1, the SDKs and wire contract and Plan 3, the dashboard inside mcpramen.

Context

Why this exists

Plan 1 produces SDKs that emit a fixed event stream. Something has to receive it, keep it, and turn it into answers. This is that something, and it is open source for two reasons: people who will not send their MCP traffic to a third party can run it themselves, and mcpramen's hosted offering is the same code with a tenancy layer around it, so there is one implementation to maintain.

Decisions already taken. Rust for the collector. Postgres as the only storage, with time-partitioned raw events plus rollup tables. Multi-tenant from the first commit. The wire contract from Plan 1 is implemented as-is; conformance fixtures from signals-spec run against this server in CI.

Architecture

One process, four jobs

                       ┌──────────────────────────── signals (one binary) ────────────────────────────┐
  SDKs ── POST ──────▶ │ ingest handler ─▶ validate ─▶ enrich (ip hash, caller) ─▶ COPY into events_* │
                       │        │ rejects per event        key lookup, rate limit                      │
                       │        ▼                                                                       │
                       │  broadcast (tokio) ─▶ SSE /live  ◀── LISTEN/NOTIFY (other replicas)            │
                       │                                                                                │
  dashboard / platform │ read API ◀── rollup tables (fast) ── raw events (recent, filtered)             │
  ── GET ────────────▶ │                                                                                │
                       │ workers (advisory-locked): rollup every 60 s · partition manager · retention   │
                       └──────────────────────────────────────┬─────────────────────────────────────────┘
                                                              ▼
                                                    Postgres 16 (one database)

Multiple replicas are safe: ingest is stateless, workers coordinate with pg_try_advisory_lock, live tail fans out through LISTEN/NOTIFY with compact payloads (project id and event ids; the SSE handler reads the rows).

Tenancy & keys

Tenants, projects, keys, users

tenants   (id, slug, name, external_id, ip_salt bytea, created_at)
projects  (id, tenant_id, slug, name, retention_days default 30, rate_events_per_min default 600,
           rate_bytes_per_min default 5_242_880, created_at, deleted_at)
api_keys  (id, project_id, key_id text unique, secret_hash bytea, scopes text[], label,
           created_at, last_used_at, revoked_at)
users     (id, tenant_id, email unique, password_hash, role check in ('owner','viewer'), created_at)
callers   (id, project_id, kind check in ('key','subject','network'), external_id, label,
           first_seen, last_seen)                       -- the "who"; one row per distinct identity
  • Key format sgk_<key_id>_<secret>. Lookup by key_id, constant-time compare of sha256(secret). The secret is 32 random bytes, so a fast hash is enough; argon2 is reserved for human passwords.
  • Scopes: ingest (POST events, whoami), read (read API for the key's project). A key never spans projects.
  • Admin token (SIGNALS_ADMIN_TOKEN): tenant and project provisioning, key minting, user creation. Never used for reading data in steady state. mcpramen's API uses it only when a project is first published.
  • Dashboard login: local users per tenant with argon2 passwords and a signed, HttpOnly session cookie. A fresh install creates the first owner from SIGNALS_BOOTSTRAP_EMAIL / _PASSWORD or via signals user create.
  • Caller identity is resolved on ingest to a callers row: a key id from caller.key_id, else a subject, else hmac_sha256(tenant.ip_salt, ip) with the user agent family. The raw IP is never written anywhere, including logs.
Ingest path

From request to rows

  1. Limits first. Body cap 1 MB after decompression, 1000 events, request timeout 10 s. Oversize → 413.
  2. Authenticate. Key lookup (cached 30 s in-process), revoked → 401, missing ingest scope → 403. last_used_at updated at most once a minute per key.
  3. Rate limit. Fixed one-minute windows per key, counted in Postgres with a single INSERT … ON CONFLICT DO UPDATE … RETURNING, so self-hosters need no Redis. Over limit → 429 with Retry-After. Store trait allows a Redis implementation later.
  4. Validate per event against the JSON Schema; then timestamps: ts more than 5 minutes in the future → ts_future; older than the project's retention → ts_too_old; the same id twice in one batch → duplicate_in_batch. Each failure fills one rejected[] entry; the rest proceed.
  5. Enrich. Resolve callers row (upsert, cached), hash IP, compute received_at = now(), record skew from sent_at as a gauge.
  6. Write. COPY … FROM STDIN (binary) into the parent events table inside one transaction; Postgres routes rows to partitions. If the COPY fails (for example a missing partition), ensure partitions for the batch's date range under an advisory lock, then retry once; if a row still fails, fall back to row-by-row inserts and reject the offenders individually.
  7. Respond 202 with counts; publish compact notices to the in-process broadcast and NOTIFY signals_live.

Target: a single replica sustains 5 000 events/s on a 2-vCPU container with p99 ingest latency under 50 ms, measured by a k6 script in the repo.

Storage

Raw events, partitioned by day

CREATE TABLE events (
  project_id   uuid        NOT NULL,
  ts           timestamptz NOT NULL,          -- SDK event time (never rewritten)
  received_at  timestamptz NOT NULL,          -- collector clock; drives rollups
  id           uuid        NOT NULL,
  type         text        NOT NULL,
  session_id   text,
  caller_id    bigint      REFERENCES callers(id),
  tool         text,                          -- tool / prompt name or resource uri, denormalised for indexes
  duration_ms  integer,
  is_error     boolean,
  client_name  text,
  client_version text,
  attrs        jsonb       NOT NULL,
  UNIQUE (project_id, ts, id)                 -- partition key must be part of any unique constraint
) PARTITION BY RANGE (ts);

CREATE TABLE events_default PARTITION OF events DEFAULT;   -- safety net; drained by the partition manager
-- events_2026_10_01 … created 3 days ahead and on demand

CREATE INDEX ON events (project_id, ts DESC);
CREATE INDEX ON events (project_id, type, ts DESC);
CREATE INDEX ON events (project_id, session_id) WHERE session_id IS NOT NULL;
CREATE INDEX ON events (project_id, tool, ts DESC) WHERE tool IS NOT NULL;
  • Idempotency is (project_id, ts, id), which is why Plan 1 forbids rewriting ts. Replays hit ON CONFLICT DO NOTHING in the fallback path and are silently skipped by COPY's pre-check (a SELECT of existing ids for the batch).
  • Partition manager (worker, every 10 minutes and on demand from ingest): create daily partitions for today + 3 days; move any rows out of events_default into their proper partition; drop partitions older than the longest retention among projects that have data in them. Rows of projects with shorter retention are deleted by a daily DELETE … WHERE project_id = $1 AND ts < $2 per partition, batched.
  • Sizing: around 350 bytes per event with indexes. 10 M events/day ≈ 3.5 GB/day raw. Rollups are a few MB/day per project regardless of volume.
  • Store trait: trait EventStore { ingest, query_events, query_sessions, … } with the Postgres implementation as the only one in v1. Rollup readers go through the same trait so a ClickHouse implementation can swap in later without touching handlers.
Rollups & retention

Pre-aggregates that converge

rollup_project_hourly (project_id, hour, requests, errors, tool_calls, sessions, unique_callers,
                       by_client jsonb, duration_hist int[])          PRIMARY KEY (project_id, hour)
rollup_tool_hourly    (project_id, hour, tool, calls, errors, duration_sum, duration_max,
                       duration_hist int[])                            PRIMARY KEY (project_id, hour, tool)
rollup_caller_daily   (project_id, day, caller_id, calls, errors, sessions, last_seen)
                                                                       PRIMARY KEY (project_id, day, caller_id)
sessions              (project_id, session_id, started_at, ended_at, caller_id, client_name,
                       client_version, calls, errors, transport)        PRIMARY KEY (project_id, session_id)
rollup_cursor         (name PRIMARY KEY, received_at_watermark)
Driven by received_at, not by ts. An SDK that backs off during a collector outage delivers events whose ts may be hours old. A "recompute the last two hours of ts" job would never see them. Instead each tick selects DISTINCT (project_id, date_trunc('hour', ts)) for rows with received_at > watermark, recomputes exactly those buckets from raw events, upserts them, and advances the watermark. Any lateness inside the retention window converges; the job is idempotent and restart-safe.
  • Latency histograms are fixed log-spaced buckets (1 ms … 60 s, 24 buckets) stored as int[]; p50/p95/p99 are interpolated from them at read time, which is cheap and merges across hours.
  • Sessions are upserted from session.* events plus a sweep that closes synthetic sessions idle for 30 minutes.
  • Retention: raw events per project (retention_days, default 30, minimum 1); rollups kept 400 days by default; sessions follow the raw retention.
  • Correctness test: a property test seeds random events with random lateness and asserts rollups equal a brute-force SQL over raw rows after the worker runs to quiescence.

Frontend: decision required

Option A · React + Vite SPA, embedded (recommended)
  • Built to static files and embedded with rust-embed; the shipped artefact is still one Rust binary.
  • The screens are also published as @mcpramen/signals-ui, a component package with no router and no fetching (it takes a typed client), so Plan 3 mounts the same screens inside mcpramen's Next.js app and themes them with its tokens. One UI, maintained once.
  • Charts hand-drawn in SVG following the dataviz rules mcpramen already uses for its admin screens; no chart dependency.
Option B · Leptos (all-Rust, client-side rendered)
  • Single language in the repo, shared types with the server, WASM bundle served by the binary.
  • Cannot be reused inside mcpramen's Next.js app; Plan 3 would re-implement every screen on the platform's own chart components, and the two would drift.
  • Smaller ecosystem for tables, virtual lists and date pickers; slower iteration for a dashboard-heavy product.

Recommendation: Option A. The backend is Rust either way; the frontend choice is about where the screens can be reused, and Plan 3 needs them in a React app.

Operations

Running it

# docker-compose.yml shipped in the repo
services:
  signals:
    image: ghcr.io/<owner>/signals:1
    environment:
      DATABASE_URL: postgres://signals:signals@postgres/signals
      SIGNALS_ADMIN_TOKEN: change-me
      SIGNALS_BOOTSTRAP_EMAIL: you@example.com
      SIGNALS_BOOTSTRAP_PASSWORD: change-me-too
      SIGNALS_PUBLIC_URL: http://localhost:8080
    ports: ["8080:8080"]
    depends_on: { postgres: { condition: service_healthy } }
  postgres:
    image: postgres:16
    environment: { POSTGRES_USER: signals, POSTGRES_PASSWORD: signals, POSTGRES_DB: signals }
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck: { test: ["CMD-SHELL", "pg_isready -U signals"], interval: 5s }
volumes: { pgdata: {} }
  • signals serve runs migrations on start unless SIGNALS_MIGRATE=false.
  • Config entirely via environment; every variable documented in docs/config.md with defaults.
  • Metrics at /metrics: ingest requests/events/rejects by reason, queue depth of the broadcast, rollup lag seconds, partition count, default-partition rows (should be zero), DB pool usage. Traces via OTLP when OTEL_EXPORTER_OTLP_ENDPOINT is set.
  • Health: /healthz (process up) and /readyz (DB reachable, migrations current).
  • Graceful shutdown drains in-flight ingest requests for up to 10 s; workers release their advisory locks.
  • Backups are Postgres backups; nothing lives outside the database.

Risks

What could go wrong

RiskMitigation
Hot partitions and index bloat at high volumeDaily partitions keep indexes small; autovacuum settings per partition documented; a weekly REINDEX CONCURRENTLY job is optional and documented.
Rollup lag under bursty ingestWatermark-based job is incremental; lag is a metric with an alert example; the dashboard shows "data up to HH:MM".
Postgres-only aggregation hits a ceiling for very large tenantsStore trait and rollup-first reads mean ClickHouse can be added behind the same API without changing the dashboard or SDKs.
Dashboard reuse in Plan 3 constrains the UI packageThe package is data-in, pixels-out with CSS variables; mcpramen tests it in its own app during C3 rather than after.
Rust team sizeThe server is deliberately small (handlers, workers, SQL); sqlx compile-time checks and the conformance suite catch most regressions without deep Rust expertise.

Reference

Terms a new developer will meet

Declarative partitioning
Postgres splits a table into child tables by a key range; here one child per day of ts. Unique constraints must include the partition key.
Default partition
A catch-all child that receives rows no other partition matches; keeps ingest from failing while the proper partition is created.
Advisory lock
pg_try_advisory_lock(key): an application-defined lock held by one connection; used so only one replica runs a worker at a time.
Watermark
The received_at up to which a worker has processed rows; stored in rollup_cursor.
Keyset pagination
Cursor = the last row's (ts, id); the next page is WHERE (ts, id) < cursor. Stable under inserts, unlike offsets.
LISTEN/NOTIFY
Postgres pub/sub; payload limited to 8 000 bytes, so notices carry ids and the receiver reads rows.
rust-embed
Compiles static files into the binary so the dashboard ships inside it.
